# Sales AX — 업무 흐름과 개발 순서

기준일: 2026-11-02 KST. 목표는 고객 정의부터 미팅 후 다음 행동까지 이어지는 아웃바운드 운영이다. Instagram·Threads 콘텐츠 제작은 이번 제품 범위에서 제외한다.

## 1. 시작 경험

첫 화면의 질문은 **“이번에 만나고 싶은 고객은 누구인가요?”**다. 사용자가 채팅으로 업무 목적·고객 설명·기존 사례를 적으면 AI가 다음 구조의 초안을 만든다. 사용자 확인 전에는 확정 ICP로 저장하지 않는다.

| 항목 | 저장할 내용 |
|---|---|
| 고객 A | 업종, 역할, 문제, 현재 사용하는 도구, 공개 활동, 연락 가능한 업무 경로 |
| 우리 제안 | 상품, 해결하는 문제, 공동 사업/교육 제안, 승인된 사례 |
| 적합 기준 | 필수 조건, 가점 조건, 배제 조건, 확인이 필요한 정보 |
| 페르소나 | 공개 근거가 있는 사실, 문제 가설, 구매/협업 가설을 분리 |
| 조사 계획 | 검색어, 조사할 공개 출처, 필요한 근거, 수집 범위 |
| 제안 구성 | 공통 파트, 고객군별 파트, 개인별 파트, CTA |

현재 고객 A의 근거는 첨부 명세에 기록된 현업 전문가·대표다. 노하우를 AI 업무 시스템과 공동 교육으로 연결하는 전문가 파트너십을 우선한다. ‘포스테디·미라’의 구체 UI/기능은 아직 조사하지 않았으므로 그대로 복제한다고 가정하지 않는다. 과거 전체 대화를 복원했다고 주장하지 않는다.

## 2. 하나의 캠페인 안에서 이어지는 업무

1. **고객 정의 채팅 → ICP 확정.** 이해한 내용을 카드로 보여주고 사람이 수정·확정한다. 수정 시 버전을 보존한다.
2. **후보 확보 → 중복·수신거부 검사.** 공개 업무 출처, 제공된 목록, 읽기 전용 Sheets 등 허용된 경로를 사용한다. 인플루언서도 별도 영업 모션으로 분리한다.
3. **조사 → 평가.** 사실에는 URL·확인 시각을 붙이고 가설은 표시한다. 타깃 적합성과 검증된 연락처를 따로 평가한다. 데이터 부족은 보류한다.
4. **개인화 제안 준비.** 공통 상품 설명을 재사용하고 개인별로 연락 이유·문제 가설·제안 아이디어·CTA를 생성한다. 개인화 강도에 따라 별도 처리한다.
5. **소개서 구성.** 사용자가 제공한 PPTX/PDF 원본을 등록한다. 모범AI·조코딩 AX 파트너스·다른 회사 자료도 사용 권한을 확인한 뒤 참고/템플릿 용도를 구분한다. ‘공통 / 세그먼트 / 개인화’ 영역을 매핑하고 사본만 생성한다.
6. **이메일·PDF 검수.** 고객 이름·회사·본문·첨부 일치, 주장 근거, 수신자 1명, 중복 접촉과 수신거부를 검사한다. 원본 없는 자동 제작은 `template_missing`으로 표시한다.
7. **명시적 승인 → 예약 큐.** 수신자별 최종 본문·첨부를 확인할 수 있는 목록에서 승인한다. 승인 후 내용 변경은 승인을 무효화한다. 발송 직전에 차단 목록·계정 잔여량을 다시 확인한다. 현재 릴리스는 실제 발송 비활성화다.
8. **회신 추적 → 후속 작업.** Gmail 스레드와 RFC Message-ID를 연결한다. 질문/긍정/거절/수신거부/반송/자동 응답을 구분한다. 사람 회신이 오면 기존 무응답 후속 작업을 중지한다.
9. **되는시간 예약 → Calendar 매칭.** 실제 예약과 Calendar 이벤트를 연결한다. 같은 이름만으로 매칭하지 않으며 불명확하면 사람이 선택한다. 시간 경과는 미팅 완료가 아니다.
10. **미팅 → 회의록 → 다음 행동.** 먼저 녹음/전사 파일 수동 첨부로 시작한다. 이후 사용 중인 회의 플랫폼의 공식 녹화/전사 기능을 연결한다. 참석자 안내·동의와 저장 위치를 표시하고, 실제 기록이 없는 회의록을 만들지 않는다.
11. **비서 제안.** 합의 사항, 미해결 질문, 약속한 자료, 담당자·기한, 다음 미팅 목적을 제안한다. 후속 메일도 초안까지만 만들고 사람 승인을 받는다.

## 3. 화면 구조

메인 화면은 채팅과 캠페인 진행 상황이다. 운영 도구는 해당 캠페인 안에서 이동한다.

| 화면 | 주된 질문 |
|---|---|
| 캠페인 대화 | 누구를 만나고 무엇을 제안하나? |
| 고객 후보·CRM | 누구를 왜 포함/제외했나? |
| 조사 근거 | 어떤 사실을 확인했고 무엇은 가설인가? |
| 제안 작업실 | 어떤 템플릿의 어느 부분을 개인화했나? |
| 이메일 검수·예약 | 누가 어떤 최종 내용을 승인했고 언제 발송하나? |
| 회신·미팅 | 어떤 답이 왔고 다음 행동은 무엇인가? |
| 회의록·후속 조언 | 실제로 무엇을 논의했고 무엇을 약속했나? |
| 성과·처리량 | 얼마나 준비·승인·발송·회신·완료했고 어디서 막혔나? |

## 4. 구현 순서와 통과 조건

| 순서 | 개발 내용 | 완료를 판단하는 증거 |
|---|---|---|
| 1 | 실제 Google OAuth, 고객 1명의 PDF·Gmail 초안, 실제 Calendar 읽기 | 회사 계정으로 미발송 초안 생성·재읽기 성공, 실제 이벤트 읽기 성공, 발송 0 |
| 2 | 고객 정의 채팅·ICP/페르소나 버전, 조사·근거 | 같은 입력으로 확인 가능한 구조화 결과, 사실/가설 구분, 사람 수정 가능 |
| 3 | 원본 템플릿 1개, 공통/개인화 영역, 생성물 QA | 실제 제공된 파일로 PPTX/PDF 비교, 잘못된 이름·오버플로 차단 |
| 4 | 승인된 예약 발송·회신·되는시간/Calendar 매칭 | 중복 발송 0, 미승인 발송 0, 관련 없는 메일 매칭 0, 예약/완료 분리 |
| 5 | 50→200→2,000건 준비 부하 실험 | 사람 검수 시간, 후보→유효율, 오류율, 작업당 비용, 재시작 복구 측정 |
| 6 | 회의록 수동 입력/파일 → 요약·다음 행동 | 실제 기록과 요약 대조, 약속/가설 분리, 후속 메일 미발송 초안 |
| 7 | 2만 연락처 운영 확장 | 중복 제거·작업 큐·계정별 정책·부하·백업 복구·전달 품질 검증 |

날짜만으로 완료를 선언하지 않는다. 내일 사용 가능한 범위는 1번의 실제 연결 성공 여부로 결정한다. 외부 공유 URL은 별도 로그인·HTTPS·배포가 준비된 뒤 제공한다. 로컬 `127.0.0.1` 주소는 대표의 다른 컴퓨터에서 접속할 수 없다.

## 5. 파일 구조와 운영 원칙

현재는 단일 FastAPI와 DB로 유지하고 모듈을 업무별로 구분한다. 마이크로서비스를 먼저 만들지 않는다.

| 구역 | 역할 | 운영자가 알아야 할 점 |
|---|---|---|
| `web/` | 화면·사용자 입력 | 여기 변경이 화면을 바꾼다 |
| `ax/api.py`, `ax/integrations.py` | 화면과 업무 기능 연결 | 버튼이 실제 어떤 API를 호출하는지 확인한다 |
| `ax/service.py` | 고객·초안·승인·미팅 규칙 | 승인·중복·상태 규칙의 중심 |
| `ax/gmail.py`, `ax/oauth.py`, `ax/google_readonly.py` | Google 연결 | 계정·권한·연결 상태를 실제 호출로 확인한다 |
| `ax/db.py`, `ax/migrations.py` | 데이터 구조와 변경 이력 | DB 파일을 지우거나 스키마를 임의 교체하지 않는다 |
| `tests/` | 통합 규칙 검증 | 테스트 통과와 라이브 연동 성공을 구분한다 |
| `vendor/` | 원본 코드 읽기 참조 | 기존 테스트를 유지하고 자동 발송 코드를 직접 노출하지 않는다 |
| `data/` | 로컬 운영 DB·비공개 설정 | GitHub에 올리지 않으며 별도 백업한다 |
| `docs/`, `artifacts/` | 개발 판단 근거·검증 결과 | 대표와 기능 범위와 실패 항목을 공유한다 |

작업량이 늘면 연구·렌더링·발송을 영속 작업 큐로 분리하고 팀 운영 DB를 PostgreSQL로 옮긴다. 먼저 현재 처리량을 측정한 뒤 전환한다. 외부 서비스 연결은 어댑터로 유지한다.

## 6. 운영자가 우선 배울 내용

프레임워크 전체보다 ‘한 고객의 데이터가 어디서 어디로 이동하는가’를 먼저 익힌다.

| 순서 | 이해할 개념 | 실습 |
|---|---|---|
| 1 | 화면 ↔ API ↔ DB | 고객 1명을 추가하고 Contact ID·Lead ID·기록을 따라간다 |
| 2 | Git의 커밋·브랜치·복구 | 변경 내용을 보고 안전한 브랜치에서 수정, 이전 버전으로 되돌려 본다 |
| 3 | OAuth·토큰·환경변수 | API 키와 OAuth의 차이, 어느 회사 계정이 어떤 권한을 줬는지 확인한다 |
| 4 | 상태·이벤트·중복 제거 | 초안 생성이 발송과 다른 이유, 같은 이벤트 재수집이 왜 0건이어야 하는지 확인한다 |
| 5 | 큐·재시도·불명확한 결과 | 네트워크 실패 후 재발송하지 않고 확인 대기로 남기는 동작을 익힌다 |
| 6 | 비용·처리량·품질 | 50명 실험의 시간·비용·검수 수정률을 기록하고 200명 추정과 비교한다 |
| 7 | 배포·로그·백업 | 서비스를 재시작하고 오류를 찾고 테스트 DB의 백업을 복원한다 |

Codex에 작업을 맡길 때는 매번 ‘변경 범위, 인수 조건, 테스트 결과, 실제 연결 결과, 실패/보류, 되돌리는 방법’을 함께 요구한다. 코드 줄 수보다 이 여섯 항목을 이해하면 운영 통제력이 생긴다.
