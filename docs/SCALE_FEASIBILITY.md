# 주 200명 → 일 2,000명 / 주 20,000명: 개발 가능성 검증

기준: 2026-11-02. 여기서 인원은 SaaS 가입자가 아니라 **중복 제거한 영업 연락처 수**다. 개발 가능한 설계와 현재 입증된 성능을 분리한다.

## 판단

**후보 확보·조사·개인화 초안 준비를 대량 처리하는 시스템은 개발할 수 있다. 하지만 현재 구현은 일 2,000명 처리나 주 2만 명 실제 발송을 입증하지 않았다.** 기존 주 200명 수작업만으로 100배 자동화를 보장할 수 없다.

특히 Gmail 한 계정으로 주 2만 명에게 수신자별 메일을 보내는 목표는 현재 공개된 계정 한도와 맞지 않는다. 대량 준비, 승인, 허용된 발송, 실제 도달, 회신·미팅 처리량을 각각 따로 설계해야 한다.

## 1. 현재 근거의 범위

| 근거 | 알 수 있는 것 | 알 수 없는 것 |
|---|---|---|
| 사용자의 주 200명 수작업 경험 | 기존 업무량 기준선 | 단계별 시간·원가·순수 신규 연락처 수 |
| 별도 212명 발송 / 207 유효 / 16 회신 / 9 미팅 약속 스냅샷 | 해당 범위의 과거 퍼널 | 대량 자동화 처리량, 확대 후 전환율, 실제 완료 미팅 수 |
| 원본 통합 Sheet 9명과 발송 이벤트 ID | 좁은 배치의 실제 기록과 재수집 기반 | 212명 전체와의 완전한 일치, 전체 영업 DB |
| 원본+통합 테스트 65개 통과 | 테스트한 규칙의 동작 | 라이브 OAuth·실제 초안 처리량·전달 품질 |
| 실제 Gmail/Calendar 커넥터 조회 성공 | Codex 연결에서의 읽기 가능 | 로컬 서비스의 연결·상시 운영 가능 |

16/207 약 7.73%, 9/207 약 4.35%는 해당 스냅샷의 단순 비율이다. 새로운 2만 명에게 같은 비율이 유지된다는 예측으로 사용하지 않는다. 미팅 약속은 실제 미팅 완료와 별도다.

## 2. 목표를 같은 단위로 비교

| 목표 | 필요한 처리량 | 현재 주 200명 대비 |
|---|---:|---:|
| 일 2,000명 × 주 5일 | 주 10,000명 | 50배 |
| 일 2,000명 × 주 7일 | 주 14,000명 | 70배 |
| 주 20,000명 / 주 5일 | 하루 4,000명 | 100배 |
| 주 20,000명 / 주 7일 | 하루 약 2,858명 | 100배 |

‘하루 2,000명’과 ‘일주일 2만 명’은 같은 목표가 아니다. ‘신규 고객 인원’과 ‘후속 포함 메일 통수’도 다르다. 고객당 총 세 통을 보낸다면 총 2만 통은 약 6,667명분의 시퀀스에 해당한다는 단순 산술도 따로 고려한다.

## 3. 외부 시스템의 확인된 제약

### Gmail 발송량

Google의 현재 Workspace 문서에는 일반 계정의 하루 메시지 한도 2,000통, mail merge 1,500통, 체험 계정 500통이 기재되어 있다. 일 단위는 자정 초기화가 아니라 연속 24시간이며 별칭의 발송도 계정 한도에 포함된다. 실제 회사 계정에 해당되는 한도는 추가 확인해야 한다.

따라서 2,000통은 ‘신규 고객 2,000명 + 후속 + 일반 업무 메일’의 안전한 운영 목표가 아니다. 정상적인 계정·발송 서비스 정책 안에서 별도 발송 어댑터와 용량 계획이 필요하다. 계정이나 도메인 추가로 제한을 우회하는 방식을 제품의 해결책으로 삼지 않는다.

출처: [Google Workspace 발송 한도](https://knowledge.workspace.google.com/admin/gmail/gmail-sending-limits-in-google-workspace).

### API 처리량과 발송량은 다르다

신규 Cloud 프로젝트에 적용되는 Gmail API 공개 수치는 사용자·프로젝트당 분당 6,000 quota units다. `drafts.create`는 10, `drafts.get`의 raw/full은 60, `drafts.send`는 100 units다. 수신자별 초안 생성+raw 재검증은 최소 70 units이므로 단순 이론 상한은 약 85건/분이다. 여기에 읽기·검색·업데이트·오류 재시도·네트워크 지연이 더해진다.

이 산술은 실제 벤치마크가 아니며 일일 발송 한도를 늘려 주지도 않는다. 준비 API 속도보다 연락처 확보·근거 품질·검수·도달 품질이 먼저 병목일 수 있다.

출처: [Gmail API quotas](https://developers.google.com/workspace/gmail/api/reference/quota).

### 전달 품질

Google은 스팸 신고율을 0.1% 미만으로 유지하고 0.3%에 도달하지 않도록 권고한다. 일정 규모 이상 발송에는 추가 인증·구독해지 요건이 있다. 수신 정책과 제공자 정책을 충족한 실제 발송만 계획한다. API 성공은 받은편지함 도달을 입증하지 않는다.

출처: [Gmail 발신자 FAQ](https://support.google.com/mail/answer/14229414?hl=en), [발신자 가이드](https://support.google.com/mail/answer/81126?hl=en).

## 4. 사람 검수는 100배로 빨라지지 않는다

다음은 **가정 기반 계산**이며 현재 실측이 아니다.

| 가정 | 일 2,000건 | 주 20,000건 |
|---|---:|---:|
| 사람 검수 30초/건 | 16.7시간 | 166.7시간 |
| 사람 검수 5초/건 | 2.8시간 | 27.8시간 |
| 자동 조사 60초/건, 직렬 실행 | 33.3시간 | 333.3시간 |

공통 문구·슬라이드는 미리 승인하고 개인별 차이와 근거를 빠르게 비교하는 검수함이 필요하다. 최종 수신자·본문·첨부를 확인 가능한 선택 승인으로 운영하며 승인 없는 발송을 허용하지 않는다. 대량으로 만들 수 있다는 이유로 검수 시간을 0으로 가정하지 않는다.

자동 조사 60초를 가정하면 2,000건을 8시간에 준비하려면 이상적으로 약 5개 동시 작업 슬롯이 필요하다. 20,000건/주40시간은 약 9개다. 실제로는 출처별 제한·여러 검색·PDF 변환·재시도 때문에 추가 자원이 필요하며 공급자 quota와 비용을 먼저 측정해야 한다.

## 5. 고객 확보량이 먼저 충분해야 한다

중복·연락처 검증·ICP 평가를 모두 통과하는 비율을 q라고 하면:

`필요 후보 수 = 목표 신규 유효 연락처 수 / q`

주 2만 명이 목표일 때 통과율이 50%면 후보 4만, 25%면 후보 8만 명이 필요하다. 두 수치는 예시 가정이다. 특정 전문가 고객군에 해당 풀이 실제로 존재하는지, 허용된 데이터 접근 경로로 매주 확보할 수 있는지는 아직 측정하지 않았다.

‘이름 2만 개’나 ‘중복 메일 2만 통’은 이 목표 달성이 아니다. 신뢰할 수 있는 데이터 공급·정규화·중복 제거·공개 연락 근거와 최신성 관리가 제품의 핵심이다.

## 6. 개발에 넣을 처리량 계측

모든 작업에 `campaign_id`, `contact_id`, 단계, 시작/종료 시각, source, 재시도 횟수, 성공/보류 사유, 실제/데모 구분을 기록한다.

| 지표 | 의미 |
|---|---|
| 후보 확보량, 고유 고객 비율 | 실제 새로운 사람이 얼마나 있는가 |
| 연락처 검증률, ICP 적합률 | 사용 가능한 고객이 얼마나 남는가 |
| 조사·문서·초안 단계별 p50/p95 시간 | 느린 작업이 무엇인가 |
| 근거 오류·고객명 혼입·수신자/첨부 오류 | 대량화로 품질이 무너지는가 |
| 승인률·수정률·사람 검수 분/고객 | 사람 업무가 실제 얼마나 줄었는가 |
| 후보당·유효 연락처당·승인 초안당 비용 | 실패·중복까지 포함한 원가 |
| 발송·반송·사람 회신·긍정·예약·완료 | 실제 사업 성과 |
| 재시작 후 중복 작업/발송 | 실패해도 안전하게 복구하는가 |

## 7. 확대 실험과 판단 기준

1. **10명 실제 종단 실험.** 고객·근거·실제 PDF·미발송 Gmail 초안을 검증한다. 초안 생성량을 발송 실적으로 표시하지 않는다.
2. **50명 소규모 실제 실험.** 계정·수신자별 승인 범위 안에서 시행하며 사람 시간·원가·수정률을 측정한다. 실제 발송은 별도 승인된 항목만 수행한다.
3. **200건 준비·복구 실험.** 실제 출처에서 준비할 수 있는지, 중복·오류·수동 보류량을 측정한다.
4. **2,000건 dry-run 부하 실험.** 가상 발송 어댑터로 작업 큐·재시도·한도 차단을 검증한다. 가상 데이터는 `is_mock=true`; 실적에서 제외한다. 동시에 실제 후보 확보량은 별도 소규모 샘플로 검증한다.
5. **실제 허용 용량 단계 확대.** 자료 공급량·제공자 정책·계정 한도·검수 가능량·반송/신고/회신 품질을 모두 만족할 때만 확대한다.

중복 발송·미승인 발송·다른 고객 첨부 혼입은 0건이어야 한다. 처리 속도·비용·수정률의 허용치는 50명 실측 뒤 고정한다. 실패한 검증을 숨기고 2만 명 목표 달성으로 보고하지 않는다.

## 결론

서버에 연락처 2만 개를 저장하는 것보다 **좋은 신규 고객 2만 명을 확보하고, 검수 가능하게 개인화하고, 허용된 발송·회신·미팅 운영으로 연결하는 것**이 어렵다. 개발 목표는 이 전 과정의 처리량과 품질을 실제 수치로 증명하는 것이다. 현재는 종단 연결을 완성하는 단계이며, 100배 확대의 성능 주장은 아직 할 수 없다.
